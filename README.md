# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает подключение к модулям управления отоплением. Самостоятельно подключать и настраивать модули пользователи не могут - это должен сделать специалист.
- Создание, просмотр, редактирование и удаление записей о датчиках.
- Хранение названия, типа, расположения, единицы измерения, значения, статуса и временных меток.
- Обновление сохранённого значения и статуса датчика через API.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система получает данные о температуре с датчиков, установленных в домах.
- Получение актуальной температуры через внешний HTTP API по идентификатору датчика или расположению.
- При ошибке получения актуальных показаний в запросах списка и отдельного датчика возвращаются сохранённые данные.

### 2. Анализ архитектуры монолитного приложения

- Язык программирования **Go**
- БД **PostgreSQL**
- Веб приложение написано с использованием Фреймворка **Gin**
- Для веб приложения описан Dockerfile - есть возможность собрать Docker образ и запустить контейнер с приложением.
- Бизнес-взаимодействия реализованы синхронно. HTTP-обработчики ожидают завершения запросов к БД и внешнему API температуры. При этом HTTP-сервер поддерживает конкурентную обработку запросов.
- Структура приложения следующая:
	- `main.go` — сборка зависимостей, маршрутизация, запуск и остановка;
	- `handlers/` — HTTP-обработчики, проверка входных данных и координация операций;
	- `services/temperature_service.go` — клиент внешнего API температуры;
	- `db/` — SQL-запросы и работа с пулом соединений;
	- `models/` — структуры данных и модели запросов.
- Компоненты системы:
	- Внешние клиенты. Взаимодействие: `клиент -- HTTP API --> приложение`.
	- Датчики температуры. Взаимодействие: `приложение -- HTTP API --> сервис получения данных температуры для разных устройств (temperature_service)`.
	- БД. Взаимодействие: `приложение -- SQL TCP --> БД (postgres)`.

### **4. Проблемы монолитного решения**

1. Получение телеметрии связано с обработкой пользовательских запросов.  
При чтении списка датчиков приложение последовательно запрашивает актуальные показания каждого температурного датчика. Время ответа растёт с количеством устройств и зависит от доступности внешнего API. В текущей реализации тайм-аут отдельного HTTP-запроса составляет 10 секунд.

2. Нет независимого сбора и истории телеметрии.  
Показания запрашиваются при обращении клиента, а полученные значения не сохраняются в БД. Таблица sensors хранит только одно значение на датчик. Этого недостаточно для просмотра истории, анализа изменений и автоматизации на основе непрерывного потока измерений.

3. Ошибки внешнего источника температуры ухудшают работу пользовательского API.  
Недоступный или медленный источник увеличивает задержку ответа. При ошибке приложение возвращает сохранённые значения без отдельного признака неудачного обновления. Получение телеметрии и её чтение пользователями не изолированы друг от друга.

4. Модель устройств ориентирована на температурные датчики.  
В коде явно определён только тип temperature, а интеграция реализована через один HTTP API. Нет модели возможностей устройств и расширяемых адаптеров стандартных протоколов. Подключение освещения, ворот, камер и новых типов оборудования потребует изменения существующего приложения.

5. Отсутствует пользовательское самообслуживание при подключении оборудования.  
Создание записи о датчике не обеспечивает подключение физического устройства. Нет проверки владения, привязки к дому и настройки взаимодействия. По текущему бизнес-процессу установка требует выезда специалиста, что ограничивает скорость подключения новых клиентов и регионов.

6. Не реализовано разграничение клиентов и их ресурсов.  
В предоставленной модели данных отсутствуют пользователи, дома, принадлежность устройств и права доступа; в HTTP API нет соответствующих проверок. Для SaaS необходима изоляция данных и команд разных клиентов.

7. Функциональность развёртывается и масштабируется единым приложением.  
Все обработчики входят в один исполняемый файл. После добавления новых функций их выпуск и масштабирование останутся связанными. При этом команды управления, поток телеметрии и видеонаблюдение имеют разные требования к ресурсам и задержкам.

8. Нет механизма выполнения пользовательских сценариев.  
В приложении отсутствуют модели правил, триггеров и механизм их выполнения. Целевое требование автоматизации потребует отдельной ответственности за обработку событий и координацию команд различным устройствам.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
