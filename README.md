# Тёплый дом

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**По бизнес-описанию:**

- Пользователь удалённо включает и выключает отопление, просматривает температуру дома через веб-интерфейс.
- Установку и подключение оборудования выполняет специалист; самостоятельного подключения нет.
- Сервер инициирует команды оборудованию и запросы показаний.

**Что представлено в учебном коде:**

- CRUD записей о датчиках: название, тип, расположение, единица измерения, значение, статус и временные метки.
- Чтение списка или отдельного датчика с синхронным запросом свежей температуры через внешний HTTP API.
- Получение температуры по расположению и обновление сохранённого значения/статуса через API.
- При ошибке источника температуры исходный код возвращал сохранённую запись без признака неудачного обновления.

В исходниках нет веб-интерфейса и команд включения отопления: эти функции заданы бизнес-описанием. Создание записи о датчике не является физическим подключением, а `PATCH /value` не управляет реле. Исходный комплект содержит Postman-коллекцию, а не Swagger-спецификацию.

### 2. Анализ архитектуры монолитного приложения

- Язык программирования **Go**
- Фреймворк **Gin**
- Одна БД **PostgreSQL**
- Модули и компоненты
	- `main.go` собирает зависимости и запускает HTTP-сервер
	- `handlers/` обрабатывает запросы;
	- `db/` выполняет SQL;
	- `models/` описывает данные;
- `TemperatureService` — HTTP-клиент источника температуры.
- Обработчики напрямую вызывают БД и клиент температуры.
- Внутри одного запроса операции выполняются последовательно и синхронно.
- Все функции выпускаются одним исполняемым файлом/образом. Для текущего одноконтейнерного развёртывания релиз требует перезапуска всего приложения.
- Можно масштабировать всё приложение репликами, но нельзя независимо масштабировать только сбор показаний или управление устройствами.

**Плюсы:** простая сборка и эксплуатация, мало инфраструктуры, локальные вызовы внутри приложения, понятная модель данных и транзакции одной БД. Для исходных 100 клиентов и 100 устройств такая архитектура может быть достаточной. Но для новых бизнес требований этого недостаточно.

### 3. Определение доменов и границы контекстов

### As-Is

Предметный домен — **удалённое управление отоплением дома**. В исходном решении есть один связанный legacy-контекст «Управление отоплением», содержащий следующие области ответственности:

| Область | Возможности | Представление в исходном коде |
|---|---|---|
| Отопление | Включение и выключение | Только бизнес-описание |
| Учёт устройств | Реестр и настройка датчиков | HTTP-обработчики и таблица `sensors` |
| Мониторинг температуры | Получение и просмотр показаний | Обработчики и HTTP-клиент температуры |

Это логическое выделение при анализе, а не DDD-контексты или сервисы.

### To-Be

Предметный домен расширяется до **модульного умного дома**:

| Поддомен / ограниченный контекст | Ответственность | Целевой сервис |
|---|---|---|
| Устройства / управление устройствами | Дома, помещения, типы, комплекты, регистрация, возможности и протокольные адаптеры | Устройства |
| Автоматизация / сценарии | Условия, расписания и выполнение действий | Модуль в сервисе устройств |
| Отопление / управление отоплением | Команды и подтверждённое состояние | Отопление |
| Освещение / управление освещением | Команды и подтверждённое состояние | Освещение |
| Ворота / управление воротами | Открытие, закрытие, запирание и отпирание | Ворота |
| Видеонаблюдение | Камеры и сеансы просмотра | Видеонаблюдение |
| Мониторинг / телеметрия | Приём, хранение и чтение показаний | Телеметрия |
| Пользователи / идентификация и доступ | Пользователи, владение, членство и права | Пользователи и доступ |
| Тарификация / подписки | Доступность функций по выбранному тарифу | Модуль в сервисе пользователей и доступа |

### **4. Проблемы монолитного решения**

1. **Показания связаны с пользовательским запросом.** Чтение списка последовательно опрашивает датчики; задержки складываются, отдельный запрос к источнику имеет тайм-аут 10 секунд.
2. **Нет независимого сбора и истории.** Свежая температура подставляется в ответ, но не сохраняется. В БД есть только одно значение на датчик, обновляемое отдельной операцией.
3. **Интеграция ориентирована на температуру.** Один специализированный HTTP-клиент, нет описания возможностей устройств и адаптеров партнёрских протоколов.
4. **Нет самообслуживания.** API записи датчика не заменяет привязку физического устройства; подключение требует специалиста.
5. **Нет изоляции клиентов.** Не моделируются пользователи, дома, владение устройствами и права доступа.
6. **Общий цикл релиза и масштабирования.** Изменения любых функций затрагивают один образ. Видео, команды и поток телеметрии имеют разные профили нагрузки.
7. **Нет сценариев и пользовательского UI в коде.** Для целевого SaaS нужны правила, триггеры, управление разными устройствами и интерфейс самообслуживания.

Часть этих пунктов — отсутствующие бизнес-возможности, которые технически можно добавить и в монолит. Основание для декомпозиции — границы ответственности, независимый сбор показаний и разные требования к нагрузке, а не сам факт появления новых функций.

# Задание 3. Разработка ER-диаграммы

![ER To-Be](/diagrams/er/er.png)

*[Картинка](/diagrams/er/er.png) - [PlantUML](/diagrams/er/er.puml)*

- **User → Home: 1:N по владению.** У дома один владелец. Дополнительный доступ нескольких пользователей задаётся **M:N** через `Membership` с ролью.
- **Home → Room / Module / Device: 1:N.** `Module` — подключённый готовый комплект партнёра. Устройство может входить в один комплект или подключаться отдельно; комплект и устройство должны относиться к одному дому.
- **DeviceType → Device: 1:N.** Тип описывается справочником, а не закрытым enum в коде. Пара `(type_id, serial_number)` идентифицирует физическое устройство и должна быть уникальной.
- **Device → Measurement: 1:N.** Показания сохраняются с временем, значением, единицей и статусом. В API `timestamp` соответствует `observed_at`, `sensor_type` — `metric`.
- **Scenario → ScenarioAction: 1:N.** В сценарии хотя бы одно действие, каждое адресовано устройству того же дома. `trigger` хранит условие или расписание в JSON.
- **Device → Configuration / ActuatorState: 1:0..1**, камера имеет **0..N** сеансов просмотра.
- У дома может быть история подписок, но не более одной действующей. `Command` и `ActuatorState` — шаблон собственных таблиц для отопления, освещения и ворот.

Это логическая модель **To-Be**. MVP ниже использует подмножество: демонстрационный дом, реестр устройств и измерения. Для простоты тип и расположение пока строковые, показание хранится в JSONB с индексируемыми ID и временем. 

Физическая структура — [init-mvp.sql](apps/init-mvp.sql).

# Задание 4. Создание и документирование API

**Тип взаимодействия**

- **REST/JSON по HTTPS** для команд и запросов с немедленным ответом: простая интеграция Go и Python.
- **AMQP/RabbitMQ в To-Be** для измерений, подтверждённых состояний и триггеров. Телеметрия и автоматизация получают события независимо от пользовательских запросов. AsyncAPI описывает этот контракт.
- **WebRTC** для видео в браузер; REST — управление сеансом, ONVIF/RTSP — взаимодействие с камерой.

Команда получает `202 Accepted`, но выполняется только после подтверждения устройства. `command_id` обеспечивает безопасный повтор. События доставляются at-least-once: получатели удаляют дубли по `event_id`, подтверждают после сохранения и отбрасывают старые состояния по `version`. Согласованность в конечном счете (eventual consistency).

**Эндпоинты**

Документированы два ключевых сервиса — устройства и телеметрия.

| Сервис | Метод и путь | Назначение |
|---|---|---|
| Устройства | `GET /api/v1/devices/{device_id}` | Сведения об устройстве |
| Устройства | `PATCH /api/v1/devices/{device_id}/value` | Обновление сохранённого снимка, без команды оборудованию |
| Устройства | `POST /api/v1/devices/{device_id}/commands` | Доставка команды через адаптер — To-Be |
| Телеметрия | `POST /api/v1/measurements` | Приём показания с защитой от дублей |
| Телеметрия | `GET /api/v1/measurements?device_id=1&limit=10` | История из БД |

[OpenAPI](schemas/openapi.yaml) - [AsyncAPI](schemas/events.asyncapi.yaml).

| Приложение | Спецификация | Swagger после запуска в MVP |
|---|---|---|
| Температура | [temperature.openapi.json](schemas/mvp/temperature.openapi.json) | [localhost:8081/docs](http://localhost:8081/docs) |
| Устройства | [devices.openapi.json](schemas/mvp/devices.openapi.json) | [localhost:8082/docs](http://localhost:8082/docs) |

# Задание 5. Работа с docker и docker-compose

Созданы:
- [FastAPI-эмулятор](apps/temperature_api/main.py) для возвращения случайной температуры.
- [Dockerfile](apps/temperature_api/Dockerfile) запускает приложение на **8081**. 
- [Docker Compose](apps/docker-compose.yml) поднимает PostgreSQL с `./smart_home/init.sql`, монолит и новые сервисы. Все данные сохраняются в volume.

Запуск из `apps/`:

```bash
docker compose up --build -d --wait --wait-timeout 180
```

# **Задание 6. Разработка MVP**

![Переходный MVP](/diagrams/mvp/mvp.png)

*[Картинка](/diagrams/mvp/mvp.png) - [PlantUML](/diagrams/mvp/mvp.puml)*

| Приложение | Реализация | Возможности |
|---|---|---|
| [Устройства](apps/devices_service/) | Python/FastAPI: API → DeviceService → DeviceRepository | CRUD, проверка полей, демонстрационный дом, произвольные типы, PostgreSQL |
| [Телеметрия](apps/telemetry_service/) | Python/FastAPI: API → MeasurementService → Repository, Collector и HTTP-адаптеры | Фоновый сбор, история, последнее значение и REST-приём по UUID |
| [Монолит](apps/smart_home/) | Go/Gin, переключаемый адаптер реестра | Сохранённый API датчиков и интеграция с новыми сервисами |

Каждый новый сервис — отдельное приложение со своим Dockerfile и классами предметной логики. По последнему уточнению проекта оба используют Python. Они запускаются в том же Compose, что и задание 5, и владеют схемами `devices` и `telemetry` одного PostgreSQL. Фоновый сбор работает без веб-клиента; история сохраняется при перезапуске и удалении устройства.
